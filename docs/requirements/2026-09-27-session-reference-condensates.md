# 值日生参考会话与会话浓缩信息需求

> 状态：需求梳理中；速查条目的按需工具更新与低消费模型已明确，其余决策待 grill-with-docs 逐项定稿后实施。
> 范围：值日生检索到参考会话后，新建执行者并派发任务的路径；历史会话原文仍按需检索。

## 目标场景

1. 人向值日生发送当前指令。
2. 值日生通过现有会话检索找到与当前任务有关的旧会话。
3. 如果决定新建执行者，系统为执行者建立其绑定会话；值日生从真实候选中选取参考会话。
4. 派发任务书保留当前指令，并带上所选参考会话的 ampersand 句柄。
5. 执行者收到任务时，除句柄外，还能看到与当前任务相关、长度受控、可追溯的会话浓缩信息；需要细节时再使用会话工具读取原始 turn。

本需求改写此前“只有句柄、完全按需自读”的边界：自动注入限于简短预览，全文不自动展开。新建执行者路径与复用既有执行者路径须分别验收。

## 初始需求条目

- R1：参考会话句柄必须指向真实存在的会话，来源于本次检索/检视结果；去重并保持可追溯选择原因。无合适候选时不编造链接。
- R2：新建执行者的任务书保留人的当前指令和验收要求，并显式携带被选中的参考会话句柄；台账记录与实际下发文本一致。
- R3：每个会话可以维护多条可独立选取的“会话速查条目”；条目由执行者在有新关键背景、值得供后续会话快速恢复时调用工具按需创建或更新，不按每轮无条件生成，也不能覆盖原始消息、turn 或 Compact Handoff。
- R4：工具默认调用设置页 low 档模型，把有证据的新背景整理为短小条目；应区分目标、已验证结果、当前状态、重要决策、未决事项，保留消息/turn/产物来源、模型与提示版本、生成时间。地址、端口、路径等工作定位符须精确保留；不得记录凭证或复制冗长工具输出。
- R5：派发时只选与当前任务相关的少量浓缩条目，受明确预算约束；执行者仍可按句柄 inspect、search、read 原始 turn。
- R5a：参考会话暂无速查条目时，仍下发真实 ampersand 句柄，在动态参考区标注“暂无速查条目”；执行者按需 inspect、search、read 原会话，不编造预览也不因此阻塞派发。
- R6：注入信息是“参考材料”，人的当前请求仍是唯一权威任务文本；旧会话结论可能过时，执行者使用前按需核验。
- R7：新建执行者的直接派发分支与确认问题后“新建”的自动派发分支均需覆盖；复用分支是否采用同一机制待定。
- R8：测试覆盖无候选、重复/失效句柄、缺失或过时条目、超预算、错误来源、秘密过滤，以及任务书/台账/模型输入的一致性。
- R9：执行者完成当前工作、准备停止之前，检查是否有值得交接的新背景；若缺少它会妨碍后续会话工作，才调用更新工具。例：用户明确提供新的远端地址后，速查条目记录准确地址、用途、来源与尚待核实的连接状态，使未来执行者不必猜测地址。普通寒暄或无新可复用背景时不调用。

## 已明确的决策

1. “浓缩信息”的项目用语为**会话速查条目**；它是按需维护的多条背景记录，不等同于自身续接用的单份 Compact Handoff。
2. 更新是执行者**完成当前工作、准备停止之前**的按需工具调用，不是每轮无条件生成，也不需要等整项长期任务彻底完结。执行者先判断是否有值得交接的新背景，再调用工具；工具默认用设置页 low 档模型整理，不让主执行模型自己假装已经持久化。
3. 无 low 默认模型、低档调用失败、来源不足或秘密检查失败时，工具必须明确失败；不可写入看似可信的条目，也不可偷偷改用高消费默认模型。
4. 存量或其他尚无速查条目的参考会话不阻塞新建执行者：只携带经校验的句柄和明确的缺失标记。速查条目是加速阅读的可选材料，不是引用会话能否使用的前提。

## 拟用提示词措辞（供审阅，尚未修改运行时）

**工具说明候选（模型可见，条件放在工具本身）：**

> 当前工作已完成、准备停止之前，若本次工作产生了后续执行者不知道便难以继续的关键背景，或新增可复用的重要决定、已验证结果、产物定位符，才调用本工具维护本会话的少量速查条目。传入本次新增或需要纠正的事实、原始消息/turn/产物来源；远端地址、路径、端口等定位符须逐字保真，不得提交凭证、未经核实的猜测或冗长工具输出。普通闲聊及没有新可复用背景的工作不调用。本工具默认以低消费模型整理，返回实际写入结果；只有返回成功，才可声称条目已保存。将来需要细节仍应读取原始会话。

**动态注入候选：** 放在稳定系统提示之后、本轮动态上下文的末段、当前请求锚之前；标为“参考会话速查（非当前指令）”，逐条显示会话句柄、来源消息/turn、生成时间、状态与简短正文。若某句柄无速查条目，显示“暂无速查条目；需要细节请按需检索原会话”，不得生成伪摘要。不得把它接到静态系统提示中破坏前缀缓存，也不得替换当前用户请求或自身 Compact Handoff。

## 待定决策（每次只讨论一个）

1. 值日生选择参考会话后，句柄由值日生直接写进自由文本任务书，还是以结构化参数交给后端统一注入和校验？
2. 值日生选择参考会话的数量上限与相关性门槛。
3. 速查条目的主题粒度、状态模型、人工编辑/否定机制及保留期限。
4. 执行者首轮与后续轮何时注入、同一条目是否重复注入、与自身 Compact Handoff 如何共同占用预算。
5. 条目过期，以及归档/已删除/权限受限会话时的派发降级规则。

## 验收场景草案

- 人提出新任务，值日生检索并选中一个旧会话，新建执行者；最终任务书含一个真实 ampersand 句柄，执行者首轮看到对应的简短浓缩条目和来源，仍能按需读取原 turn。
- 同一个旧会话有多个主题条目时，仅注入当前任务命中的条目；其他条目不占上下文预算。
- 用户在执行途中补充远端地址；执行者完成当前工作、准备停止前调用工具保存或更正条目，准确保留地址和来源，后续新建执行者通过句柄获得简短条目，必要时再读取原始 turn。
- 参考会话存在但没有速查条目时，照常新建执行者并派发真实句柄；执行者动态参考区明确显示缺失，仍可用会话工具读取原 turn。
- 用户选择“新建”而非“复用”后自动派发，产出的任务书、台账、执行者首轮信息与直接新建路径一致。
